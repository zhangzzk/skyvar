SkyVar extension note

Bias Variation from Spatially Varying Selection

Created: 2026-05-16 Updated: 2026-05-19 Status: SPS source-density caveat unresolved

Current Goal

Extend SkyVar from spatially varying n(z) to spatially varying galaxy bias with the same per-simulation-pixel population semantics as the n(z) workflow. The current canonical path draws n_pop galaxies for each seen simulation pixel, attaches systematics, runs the detection classifier, and accumulates unselected and selected redshift-binned mean-bias maps.

The first 128/128 n_pop=1,000,000 run is recorded as a luminosity-proxy baseline, not the final science run. The SPS-mass path is implemented, but the current GalSBI-SPS intrinsic source pool does not reproduce the F24 post-quality-cut source density and should not be used as the production n_pop density source until this is resolved.

Current Caveats To Resolve

  • SPS/F24 density mismatch: the F24 catalog gives 183.478 arcmin^-2 after the SkyVar quality cuts, while the one-pixel GalSBI-SPS intrinsic smoke gives 31.646 arcmin^-2 after the same cuts.
  • Not a cap/footprint issue: the same SPS smoke has intrinsic GalSBI count density 177.313 arcmin^-2, close to F24, but only 1494 / 8405 rows survive the quality cuts.
  • Likely cause: the SPS intrinsic catalog is much fainter. In the smoke, r-band int_mag median is about 29.83; in F24 it is about 26.65. Most SPS rows fail r < 28.
  • API finding: GalSBI's Tortorelli+25 mode="intrinsic" API is valid, but the SPS plugin samples from the stellar-mass function with z_sm_intp=None and does not apply the F24-like apparent-magnitude preselection before writing the intrinsic catalog.
  • Decision needed before production: either find/build a magnitude-limited SPS source-pool generation path that matches F24 after cuts, or use the F24 density for n_pop and use SPS only as the stellar-mass/bias property reservoir.
  • Current code caveat: the latest selection path reads n_pop density from the source-table summary. That is correct for a density-faithful source table, but would currently propagate the low SPS post-cut density if used directly.
  • Do not resurrect old pools: fixed-cap SPS pools are invalid for density calibration. Auto caps avoid intrinsic truncation, but they do not solve the SPS-vs-F24 post-cut density mismatch.
  • F24 density diagnostic: when measuring F24 with bias_variation.catalog density, use --quality-size-column int_r50_arcsec, SKYVAR_BIAS_SPS_QUALITY_SIZE_SCALE=1.0, and SKYVAR_BIAS_DENSITY_NSIDE=512 to match src.selection.
  • Run policy: pause large SPS production/rerun jobs until the density policy is explicit in config and job tags. One-pixel SPS smoke validates plumbing only, not source-density calibration.
  • Map interpretation: high-redshift selected bins still require selected-count or selected-weight masks before interpreting maximum selected-minus-unselected bias deltas.

Canonical Code Path

  • bias_variation/full_skyvar_bias.py: full workflow and production entry point.
  • src.systematics: builds native SkyVar systematics maps for the requested nside.
  • src.selection: source of detection and optional selection cuts.
  • bias_variation/plotting.py: profile plots, combined map panels, and pixel b(z) examples.

Bias Assignment

  • Production input catalog: GalSBI-SPS r-band source pool with log10_surviv_stellar_mass.
  • Mass source: --mass-source sps_surviving by default; luminosity proxy now requires explicit --mass-source luminosity_proxy.
  • SPS size convention: r50 * 0.168 arcsec, passed through --size-column r50 --size-scale 0.168.
  • Halo relation: inverse Moster+13 SHMR with 0.15 dex scatter.
  • Halo bias: Tinker+10 through Colossus with mdef=200c.

Plot Policy

The map plotting path has been made consistent with the compact n(z)-style review flow. Individual scalar map files are no longer the default output. The canonical map products are combined panels with histogram mini-panels, global-reference markers, and SkyVar-style HEALPix-resolution marker sizing.

  • *_map_medians_and_difference.png: unselected median, selected median, and selected-minus-unselected bias.
  • *_map_object_counts_panel.png: unselected counts, selected counts, and selected weight.
  • *_bias_profiles.png: per-redshift pixel-median bias profiles and selected-minus-unselected profile.
  • *_pixel_bz_examples.png and .csv: n(z)-style overlay with weighted global b(z) and all output-pixel b(z) curves, rebinned to 15 z bins for review by default.

Plot Review

  • The combined maps now use SkyVar-style pixel-size markers and no longer show artificial gaps between adjacent nside=128 pixels.
  • The selected global b(z) rises strongly at high redshift. This is physically consistent with detection selecting the luminous/high-bias tail, but high-z per-pixel extrema should still be interpreted with selected-count and selected-weight cuts.
  • The 128/128 baseline source-property plots are internally consistent with the old luminosity-proxy model, but should not be used for science interpretation.
  • The SPS smoke source-property plots use log10_surviv_stellar_mass; M_h follows the SHMR inversion with scatter, and bias increases with M_h and redshift.
  • The map-level median-bias panels summarize each pixel by the median over redshift bins; the pixel b(z) overlay now includes all pixels and is the clearer plot for redshift-dependent global versus pixel behavior.

Toy and Shortcut Audit

  • Removed from production default: luminosity-proxy stellar mass from abs_mag. It is now available only through explicit --mass-source luminosity_proxy diagnostic runs.
  • Production default: --mass-source sps_surviving, requiring log10_surviv_stellar_mass. Missing SPS mass now fails loudly instead of falling back.
  • Diagnostic only: old bias64 random-pixel/resampling jobs and the representative-pixel SPS products. They are not equivalent to drawing n_pop galaxies per seen simulation pixel.
  • Model assumption: 0.15 dex Gaussian scatter is applied to inferred halo mass after the Moster+13 inverse. This is kept explicit in summaries.
  • Source-pool cap: The original SPS pool used explicit 50k blue/red caps and is not valid for density calibration. Current generation uses GalSBI-derived auto caps, but the post-cut density remains too low because the intrinsic SPS catalog is too faint relative to F24.
  • Numerical approximation: SHMR inverse and Tinker+10 bias use interpolation grids by default; exact modes remain available for checks.
  • SkyVar convention: source rows are sampled with replacement and assigned local synthetic RA/DEC per chunk to preserve source density for the blend classifier, matching the n(z)-style selection workflow.
  • Plotting only: source-property scatter plots use a deterministic subsample for readability; maps and profiles use the accumulated full run.
  • Unrelated old toy modules: src/toy_variation.py and the nz_source=toy option in src/density_variation.py are not part of the bias production path.

Open Caveats

  • The completed 128/128 run is a luminosity-proxy baseline. It should be replaced by an SPS-mass rerun before science interpretation.
  • The SPS smoke run is intentionally small and validates plumbing only; it exposed a real source-density mismatch with F24.
  • The active unresolved issue is whether production n_pop should come from a corrected magnitude-limited SPS catalog or from the F24 post-cut density.
  • The current Tortorelli+25 intrinsic SPS catalog should not be treated as an F24-density source catalog at r < 28.
  • High-z selected bins still need selected-count or selected-weight masks before interpreting maximum deltas.

Next Steps

  1. Decide the density policy: corrected magnitude-limited SPS source density, or F24 density with SPS as a property reservoir.
  2. If using corrected SPS density, identify and smoke-test the correct GalSBI-SPS mode/config or custom filtering strategy that reproduces F24-like post-cut density.
  3. If using F24 density, make that explicit in config/job names and prevent source-table summaries from silently overriding n_pop with low SPS post-cut density.
  4. After the density policy is fixed, regenerate a multi-pixel SPS source pool and rerun the 128/128 SPS-mass workflow.
  5. Add a plotting or summary mask for low selected-count or low selected-weight high-z bins before interpreting maximum deltas.
